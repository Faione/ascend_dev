Add Pipeline：构建、代码与四核数据流

先看 CMake 如何生成扩展、Linux 如何将它加载到 Python 进程，再看运行时如何向 NPU 发起内核计算。固定展示 Core 0–3；没有分到 tile 的核心显示“未启动”。

构建产物 → OS 加载 → NPU 执行

① 构建阶段 · 容器 Linux 文件系统
源代码add_pipeline.cpp（内核 + 注册）
extension.cpp（Python 入口）
CMake + Bishengadd_pipeline_obj 对象文件；extension.cpp 对象文件
链接产物build/_C.so，链接 torch、torch_npu 与 CANN 库
复制到 Python 包ascend_add_pipeline/_C.so
② 加载阶段 · 容器 OS / Python 进程
Python importimport ascend_add_pipeline → 导入 ._C
Linux 动态加载器映射 _C.so 与依赖库；静态初始化执行 TORCH_LIBRARY 注册，随后 Python 调用 PyInit__C
PyTorch 算子分派torch.ops.ascend_add_pipeline.add_pipeline 对 NPU 张量分派到 AddNpu
③ 执行阶段 · NPU 设备
宿主侧发射AddNpu 取当前 NPU stream，经 torch-npu/CANN 路径发射内核
NPU 执行AI Core 读取 GM，使用 UB 队列与向量单元，写回 GM
关键边界：_C.so 是由 OS 加载到 Python 进程的共享库；NPU 不直接加载该 Linux 文件。运行时的内核发射才进入设备执行路径。

代码分析：分阶段执行流程

按一次非空 NPU 张量调用的时间顺序阅读。横向区分宿主进程、跨硬件边界的通路和 NPU；纵向是函数调用阶段。控制通路传递命令与参数，数据通路搬运张量元素。

⇢ 控制流（虚线）：地址、核数、stream、启动/同步命令→ 数据流（实线）：X/Y/Z 的实际元素
执行时机容器 OS / Python 进程交互通路NPU 设备
01 · 加载时每次进程导入扩展时
TORCH_LIBRARY_FRAGMENT / IMPL_C.so 的静态注册建立 schema、Meta 与 PrivateUse1 实现。
无硬件交互此时只在进程内建立 PyTorch 分派表。
NPU 未执行 Add没有张量数据搬运。
02 · 输入准备验证脚本，算子调用前
x_cpu.to(device)、y_cpu.to(device)CPU 张量仍用于构造参考结果，另创建 NPU 输入张量。
→ H2D 数据搬运X/Y 的实际元素从主机 DRAM 复制到 NPU GM；不属于 Add 内核。
X/Y · GM设备输入张量已就绪。
03 · 调用时每次正常 NPU 调用
torch.ops → AddNpu → CheckInputs按 PrivateUse1 选实现；检查形状、dtype、设备、连续性和梯度条件。
无张量数据搬运TORCH_CHECK 检查张量元数据；CPU 不做逐元素加法。
X/Y 已是 NPU 张量其元素留在 GM，不因参数检查读回主机。
04 · 准备时发射前
OptionalDeviceGuard、empty_like选择输入设备、分配 Z；查询平台信息，计算 tiles、tilesPerCore、blocks。
⇢ 平台信息/内存管理 APIPlatformAscendCManager 获取 AIV 数量、UB 容量；runtime 为 Z 准备设备内存。平台信息可能来自缓存，不等于每次直连硬件查询。
设备能力与 GM 输出区返回容量信息；Z 在 GM 中有可写空间，X/Y 元素不在此步参与计算。
05 · 发射时宿主侧提交命令
RunOpApi → lambdadata_ptr 取得设备地址；选择当前 NPU stream；发射 add_pipeline_kernel。
⇢ 内核启动命令经 torch-npu/CANN 路径提交 stream、block 数、GM 地址及 n/tilesPerCore。这里传的是地址和标量参数，不是 X/Y 元素本身。
NPU stream 接收工作设备按命令安排 block；宿主函数可先返回 Z 张量句柄。
06 · 设备执行各 block 独立运行
AddNpu 已提交CPU 不进入 CopyIn/Compute/CopyOut 逐元素循环。
→ NPU 内部数据流X/Y GM → qx/qy UB → 向量 Add → qz UB → Z GM；这条路径不跨主机边界，尾 tile 只搬运实际 count。
add_pipeline_kernel → Init → ProcessGetBlockIdx 定区间；TPipe/TQue 管理 UB；每 tile 调用 CopyIn → Compute → CopyOut。
07 · 同步时调用方需要结果时
torch.npu.synchronize()等待当前设备上的工作完成；这是验证脚本行为，不在 Add 内核中。
⇢ 同步控制 / ← 完成状态控制通路等待相关设备工作完成；不搬运 Z 的元素。
计算完成的 Z 位于 GM同步后可安全读取。
08 · 读回时仅验证脚本
out.cpu() → CPU 接收 Z得到主机副本，与 CPU 参考值比较。
← D2H 数据搬运Z 的实际元素从 NPU GM 复制到主机 DRAM；这与发射时传递 GM 地址不同。
Z · GM数据源留在设备全局内存。
分支：长度为 0 时，AddNpu 分配输出后直接返回，不发射内核。Meta 张量会调用独立的 AddMeta，只推断输出属性，不执行 NPU 计算。
函数内部常见 API
TORCH_CHECK / torch::Tensor张量对象提供形状、dtype、设备、步长和数据地址；检查失败时在宿主侧抛异常。
OptionalDeviceGuard / empty_like前者暂时选择输入设备并在退出时恢复；后者创建同形状、同 dtype、同设备的未初始化输出。
PlatformAscendCManager / NPUStream前者提供 AIV 核数、UB 大小；后者取得当前 NPU 命令队列以维持调用顺序。
GM_ADDR / GlobalTensor / TPipeGM_ADDR 是设备全局内存地址；GlobalTensor 提供元素索引视图；TPipe 管理 AI Core 片上 UB 队列。
TQue::AllocTensor / EnQue / DeQue / FreeTensor申请 UB 槽、交给下一阶段、取得已入队数据、归还槽；qx/qy 是输入队列，qz 是输出队列。
DataCopyPad / AscendC::Add前者在 GM 与 UB 之间搬运，blockLen 以字节计；后者在 UB 中逐元素相加，长度以元素数计。

双缓冲队列为相邻 tile 提供可轮换的槽位；代码的调用顺序并不能单独证明搬运和计算在硬件上实际重叠。

运行时：四核数据流

主机 · CPU / DRAM
X/Y · CPU 张量输入由 .to(device) 上传Z · CPU 校验结果
↓ H2D · X/Y跨主机与 NPU 设备边界↑ D2H · Z
Ascend NPU · GM + AI Core 0–3
左右两侧的 GM 为同一设备全局内存的输入/输出视图；中间紫色框是各核心独立的片上区域。
主机 DRAMNPU GM 所在设备AI Core 片上 UB + 向量单元

每个 tile 最多 1024 个 float32，qx、qy、qz 各有 2 个 UB 缓冲槽，按本核的 tile 序号轮换。H2D/D2H 属于验证脚本；CopyIn/Compute/CopyOut 属于 Add 内核。四核同步高亮是讲解方式，不代表硬件严格同步或实测性能。
