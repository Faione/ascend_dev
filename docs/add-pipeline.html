Add Pipeline：构建、代码与四核数据流

先看 CMake 如何生成扩展、Linux 如何将它加载到 Python 进程，再看运行时如何向 NPU 发起内核计算。固定展示 Core 0–3；没有分到 tile 的核心显示“未启动”。

extension.cpp（Python 入口）

② 加载阶段 · 容器 OS / Python 进程
Python importimport ascend_add_pipeline → 导入 ._C
Linux 动态加载器映射 _C.so 与依赖库；静态初始化执行 TORCH_LIBRARY 注册，随后 Python 调用 PyInit__C
PyTorch 算子分派torch.ops.ascend_add_pipeline.add_pipeline 对 NPU 张量分派到 AddNpu
③ 执行阶段 · NPU 设备
宿主侧发射AddNpu 取当前 NPU stream，经 torch-npu/CANN 路径发射内核
NPU 执行AI Core 读取 GM，使用 UB 队列与向量单元，写回 GM
关键边界：_C.so 是由 OS 加载到 Python 进程的共享库；NPU 不直接加载该 Linux 文件。运行时的内核发射才进入设备执行路径。

代码分析：函数实际调用顺序

以下是输入为非空 NPU 张量时的一次调用。注册发生在模块加载时；随后宿主侧先准备并发射，设备侧各 block 再独立处理数据。

  1. 加载时注册 · TORCH_LIBRARY_FRAGMENT / TORCH_LIBRARY_IMPL

    _C.so 加载后，PyTorch 记录算子 schema、Meta 实现和 PrivateUse1（torch-npu 的 NPU 分派键）实现。注册不是每次调用都重新执行。

  2. Python 调用 → AddNpu(x, y) · 宿主侧

    torch.ops.ascend_add_pipeline.add_pipeline(x, y) 由 PyTorch dispatcher 按输入设备选中 AddNpu。它先调用 CheckInputs，验证形状、float32、同设备、连续性和不需要梯度。

  3. AddNpu 准备输出与分块 · 宿主侧

    OptionalDeviceGuard 暂时切换到输入所在 NPU；empty_like 分配未初始化的 Z。非空时查询 AIV 核数和 UB 容量，计算总 tile、每核 tile 数与实际 block 数。

  4. RunOpApi → 发射 lambda · 宿主侧

    data_ptr<float>() 取 X/Y/Z 的设备地址；lambda 在当前 NPU stream 上以 <<<blocks, ..., stream>>> 发射 add_pipeline_kernel。此时没有在 CPU 上逐元素相加。

  5. add_pipeline_kernel → KernelAdd::Init · 设备侧

    每个 block 用 GetBlockIdx() 算自己的连续区间；Init 将 GM 地址包装成 GlobalTensor，并由 TPipe 为 qx/qy/qz 队列分配 UB 缓冲。

  6. KernelAdd::Process · 设备侧

    对本核的每个 tile 依次调用 CopyIn → Compute → CopyOut：GM 的 X/Y 进入 UB，向量单元执行 Add，UB 的 Z 写回 GM。最后一个 tile 使用实际 count，不必凑满 1024 个元素。

  7. 返回张量与读取结果 · 宿主侧

    AddNpu 返回 Z 张量不代表 NPU 已完成计算；验证脚本执行 torch.npu.synchronize()，再用 out.cpu() 读回并比较结果。

分支：长度为 0 时，AddNpu 分配输出后直接返回，不发射内核。Meta 张量会调用独立的 AddMeta，只推断输出属性，不执行 NPU 计算。
函数内部常见 API
TORCH_CHECK / torch::Tensor张量对象提供形状、dtype、设备、步长和数据地址；检查失败时在宿主侧抛异常。
OptionalDeviceGuard / empty_like前者暂时选择输入设备并在退出时恢复；后者创建同形状、同 dtype、同设备的未初始化输出。
PlatformAscendCManager / NPUStream前者提供 AIV 核数、UB 大小；后者取得当前 NPU 命令队列以维持调用顺序。
GM_ADDR / GlobalTensor / TPipeGM_ADDR 是设备全局内存地址；GlobalTensor 提供元素索引视图；TPipe 管理 AI Core 片上 UB 队列。
TQue::AllocTensor / EnQue / DeQue / FreeTensor申请 UB 槽、交给下一阶段、取得已入队数据、归还槽；qx/qy 是输入队列，qz 是输出队列。
DataCopyPad / AscendC::Add前者在 GM 与 UB 之间搬运，blockLen 以字节计；后者在 UB 中逐元素相加，长度以元素数计。

双缓冲队列为相邻 tile 提供可轮换的槽位；代码的调用顺序并不能单独证明搬运和计算在硬件上实际重叠。

运行时：四核数据流

主机 · CPU / DRAM
X/Y · CPU 张量输入由 .to(device) 上传Z · CPU 校验结果
↓ H2D · X/Y跨主机与 NPU 设备边界↑ D2H · Z
Ascend NPU · GM + AI Core 0–3
左右两侧的 GM 为同一设备全局内存的输入/输出视图；中间紫色框是各核心独立的片上区域。
主机 DRAMNPU GM 所在设备AI Core 片上 UB + 向量单元

每个 tile 最多 1024 个 float32，qx、qy、qz 各有 2 个 UB 缓冲槽，按本核的 tile 序号轮换。H2D/D2H 属于验证脚本；CopyIn/Compute/CopyOut 属于 Add 内核。四核同步高亮是讲解方式，不代表硬件严格同步或实测性能。
